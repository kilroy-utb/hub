## 0. 一句話結論

> **技術上做得出来（1–2 天），但「做成公開的找店目錄／評論平台」在 Google 條款與經濟結構上雙重站不住。**
> 真正能賺錢的版本是：**地圖與評論只當介面，價值放在你自己的後端服務**；或者**服務單一商家**（用 Business Profile API，API 成本為零）。

拆成三個子問題：

| 子問題 | 結論 | 關鍵理由 |
|---|---|---|
| ① 地圖可以撈嗎？ | ✅ 可以，但「撈」只能是單次呼叫，不能變成你的資料庫 | Maps Embed API 免費無上限；Maps JS $7/1,000；**No Caching 條款禁止你把商家資料存成自己的庫** |
| ② Google 評論可以秀嗎？ | ✅ 可以，但**每家最多 5 則**，且有一整包呈現義務 | Place Details Ent+Atmosphere $25/1,000；5 則是硬上限，**付更多錢也解鎖不了** |
| ③ 這樣的網頁能賺錢嗎？ | ⚠️ **只有特定形态能賺** | 秀評論會把流量天花板壓到 **9,181 PV/月**；只做地圖不秀評論則可撐到 44 萬 PV/月 |
| ④ 換成免費方案有救嗎？ | ⚠️ **地圖有救，評論無解** | MapLibre+OpenFreeMap 地圖端 **$0**、OSM 可合法自建目錄；但評論只能靠 Yelp Enhanced（$299/月、3 則 ×160 字元）→ 天花板解到 **145,110 PV** |

## 1. 執行摘要

### 六個核心結論

**① 技術可行性 ≈ 90%，1–2 天可做出可用原型。**
Google Maps JavaScript API + Places API 的官方範例本身就能跑起來，`Maps Embed API` 甚至免費無上限。阻擋你的從來不是工程能力。

**② 真正的一刀切在 Google Maps Platform 條款 3.2.3，其中 (d) 款是致命的。**
條款明文禁止用 Maps Core Services 建立 **"listings or directory service"（商家列表或目錄服務）**，也禁止用它建立或擴充廣告產品。你想做的那個「找店平台」，名字就寫在禁止清單上。

**③ 5 則評論上限不是限制細節，而是模型的致命傷。**
Places API (New) 的 Place Details **最多回傳 5 則評論**，依相關性排序，**沒有分頁、沒有 token、沒有排序選項**。實證資料顯示：截成 5 則後只保留 **3.6%** 的語料；**87.9%** 的商家評論會被截斷；**32.4%** 的評論只有星等沒有文字。

**④ 經濟結構是「越紅越虧」，而且有明確的天花板。**
因為 No Caching，你無法快取、无法摊平成本，成本 = 流量 × 單位成本，嚴格線性。實測：**一次評論牆檢視的 API 成本（NT$0.785）是單次廣告收益（NT$0.150）的 5.23 倍**。在 CPM NT$150 的假設下，網站的**最大可承受流量是 9,181 PV/月** —— 超過這個數，每多一個訪客就多虧一筆錢。

**⑤ 灰色地帶全部期望值為負，且隨規模遞減。**
4 個灰色模型的臨界機率 P\* 落在 **6.00% – 10.00%**，但實際被查機率是 **25% – 55%**，期望值全部為負。規模從 1 倍放大到 10 倍時，EV/(T×C) 從 −4.10 惡化到 −9.20。


**⑥ 免費替代方案能解地圖，解不了評論 —— 但它解開了「條款紅線」。**
用 **MapLibre + OpenFreeMap** 取代 Maps JS，地圖端成本直接 **歸零（$0、無上限、可商用、免綁卡）**；用 **OSM（ODbL）** 取代 Google Places 還能**合法自建商家目錄**（不受 3.2.3(d) 限制）。
但**評論沒有便宜的合法替代**：Yelp 免費層已消失（只剩 30 天試用），Enhanced $299/月才第一次拿到評論，且每則僅 160 字元、條款同樣禁止自建目錄。
**真正的關鍵不是價格，是快取權** —— Yelp 允許 24 小時快取（成本 ∝ 商家數），Google 不允許（成本 ∝ PV）：流量天花板從 **9,181 PV 解到 145,110 PV（高 15.8 倍）**。
詳見第 6 章。

## 2. 需求拆解：你說的兩件事，技術上各自成立嗎？

### 2.1 「有地圖可以撈」

「撈」有三個層級，合法性完全不同：

| 層級 | 做法 | 技術可行 | 條款判定 | 說明 |
|---|---|---|---|---|
| L1 顯示 | 嵌入 Google 地圖 iframe 或用 Maps JS API | ✅ | ✅ 合規 | Maps Embed API **免費無上限**；Maps JS API 有免費額度 |
| L2 查詢 | 用 Places API 搜尋附近商家、取得名稱地址星等 | ✅ | ✅ 合規（有條件） | 必須即時呼叫、標 Google 歸屬、不得改寫 |
| L3 蒐集 | **批次抓全台商家、存成自己的資料庫** | ✅ 技術上做得到 | ❌ **明文禁止** | No Caching + No Scraping（條款 3.2.3a、3.2.3b） |

**L3 為什麼不行 —— 三道具體限制：**

1. **No Scraping（3.2.3a）**：不得預先抓取、索引、儲存、轉發或重新託管 Maps Content；明文包含**使用者評論**。預先跑完一輪把商家資料灌進自己的資料庫，正中此條。
2. **No Caching（3.2.3b）**：不得快取 Google Maps Content。Places API 的**唯一豁免是 `place_id` 可永久儲存**；經緯度僅可暫存 30 天；**評論不在豁免清單**。
   - 實務含義：你的網站每次被造訪，都要重新向 Google 要一次評論 → 成本無法攤平 → 沒有資料庫、沒有 SEO 資產、沒有護城河。
3. **搜尋結果本身也沒有「全部」**：
   - Text Search：每頁 20 筆、單次查詢最多 60 筆
   - Nearby Search：每次最多 20 筆
   - **Nearby Search 沒有「只要 ID」的 SKU** —— 即使你只想拿 place_id 過水，一樣按 Nearby Search Pro（$32/1,000）計費
   - 要覆蓋一個縣市的商家，需要數百次分格查詢，重疊商家會被重複計費

### 2.2 「Google 評論可以秀」

可以，但有三個硬條件。

**條件一：只有 5 則。**
Places API (New) 的 Place Details 回傳評論時，**最多 5 則**，依相關性排序。**沒有分頁參數、沒有 pageToken、沒有排序選項**。Legacy Place Details 雖然提供 `most_relevant` / `newest` 排序選項，但回傳筆數上限同樣是 5 則。Google 官方文件明載：**沒有任何付費方案可以解鎖更高的上限**。

> 實作技巧：若你要「最新優先」，做法是取回那 5 則（相關性排序）後，**在本地用 `publishTime` 排序**。但那得到的是「5 則的最新排列」，**不是「最新的 5 則」**。這個差別在下面第 4 章會變成一個真實的商業問題。

**條件二：要買對 SKU。**
含評論需要 **Place Details Enterprise + Atmosphere**（$25/1,000，超過 1,000 次免費額度後）。如果你的 field mask 只要 `rating` 或 `reviews` 以外的欄位，會被歸到不同計價級距 —— **你的費用取決於你問了什麼，而不只是你用了什麼**。

**條件三：要遵守一整包呈現義務。**
Places API Policies 對評論展示的要求是強制性的，漏一項就違規：

| 義務 | 具體要求 |
|---|---|
| 顯示作者資訊 | 作者姓名 + 照片 + 個人檔案連結（空間有限時，照片至少要顯示） |
| 導向原始來源 | 提供 `googleMapsUri` 直達 Google Maps 原始評論頁 |
| 歸屬 | 顯示 Google logo 或「Google Maps」字樣，且**不得修改外觀** |
| 說明排序 | 必須說明評論的排序／篩選方式（預設為相關性排序） |
| 回報機制 | 提供 `flagContentUri` 回報連結 |
| 時間標示 | 建議顯示 `relativePublishTimeDescription` |
| 翻譯揭露 | 若做了翻譯，必須告知使用者並提供 `originalText` 原文 |
| 說明驗證方式 | 說明 Google 如何驗證評論 |

**可以合法加值的功能：AI 摘要 `reviewSummary`。**
Places API 會提供 AI 產生的評論摘要（最多 3 個主題）。但必須**逐字顯示 `disclosureText`**、標題固定用「Review summary」、附上「How Google sources and uses information in local listings」說明連結、提供回報連結與 `reviewsUri`。

### 2.3 一個容易被忽略的技術限制

**Places API (New) 不回傳商家回覆（owner response），也不回傳評論照片。**
想顯示商家回覆，得另外處理；評論照片需要用 `reviewPhotos` 搭配評分分級欄位。第三方「評論牆」產品的常見功能，API 層級其實給不了。

## 3. 三道紅線：Google Maps Platform 條款 3.2.3

這是整份報告的法遵核心。Google Maps Platform 條款的 **3.2.3 禁止行為**款列了四小項：

### 3.2.3 (a) — No Scraping（禁止抓取）
> 不得預先抓取、索引、儲存、轉發或重新託管 Maps Content。**明文包含複製儲存商家名稱、地址、使用者評論。**

**對你的影響**：任何「先跑一次程式把全台商家與評論抓回來存進 MySQL / Airtable / BigQuery」的設計，直接違規。跑完再拿來展示，和即時呼叫，條款上是兩回事。

### 3.2.3 (b) — No Caching（禁止快取）
> 不得快取 Google Maps Content。Places API 的豁免僅限於 **`place_id` 可永久儲存**；經緯度可暫存 30 天。評論不在豁免範圍。

**對你的影響**：**這條直接決定了這個生意的經濟結構**。因為不能快取：
- 成本 = 流量 × 單位成本（嚴格線性，無法用流量攤薄）
- 沒有自己的資料庫 → 沒有 SEO 資產 → 沒有自然流量 → 沒有護城河
- 每一個訪客都是淨成本

### 3.2.3 (c) — No Creating Content From Maps Content（禁止衍生創作）
> 不得用 Places API 的經緯度做 point-in-polygon 分析。EEA 版本另禁止用 Maps Content 訓練或測試 AI 模型。

**對你的影響**：想做「找出某服務範圍內的所有店」這種分析，用 Places API 的資料做就是違規（要改用合法授權的第三方資料商）。

### 3.2.3 (d) — No Re-Creating Google Products / No Directory Service ⭐ 最致命
> 不得使用 Services 建立與 Google 產品功能實質相似的產品。**明文禁止使用 Maps Core Services 建立 listings or directory service（商家列表或目錄服務）**，也禁止用它建立或擴充廣告產品。產品必須有 **substantial, independent value（實質且獨立的價值）**。

**對你的影響**：這一條是**直接命中**的。你想做的「Google Map 這樣的網頁」——一個可以撈商家、秀評論的找店平台 —— 在條款裡的正式名稱就叫「目錄服務」。這一條不是灰色地帶，是紅線。

**「實質且獨立的價值」（substantial independent value）測試**是唯一的安全港：

| 檢驗 | 會通過 | 不會通過 |
|---|---|---|
| 資料層 | 你的地圖與評論只是**佐證引用**，核心價值在你的後端（預約／報價／排隊／優惠券／回覆建議） | 網站的主體就是「地圖 + 評論列表」 |
| 流量來源 | 你的原創內容（評測、教學、排行分析）帶來流量 | 靠 Google 的資料內容本身吸引流量 |
| 資料所有 | 你的核心資料是你自己產生或合法授權的 | 核心資料就是 Google 的商家與評論 |
| 呈現方式 | 即時請求、標 Google 歸屬、不改寫 | 快取成自己的庫、自建「評論資料庫」 |

### 附帶條款：EEA 專屬限制

自 2025-07-08 起生效：**Places API 的內容不得再與任何地圖（包括 Google Map）並列顯示**，必須改用 Places UI Kit。
**台灣不在 EEA**，此條不適用；但若你的 Google Cloud **billing address 在 EEA**，則該限制會適用到你的專案。

## 4. 資料實證：5 則上限到底傷到什麼程度

以下數據來自 **justreview.co 的公開評論語料分析（2026-08-21，384,482 則評論 / 2,907 個商家）**，是檢驗「5 則上限」真實影響最直接的方式。

### 4.1 覆蓋率：只留下 3.6%

| 指標 | 數值 |
|---|---|
| 語料總量 | 384,482 則評論 / 2,907 個商家 |
| 每商家評論數 | 中位 **37**、p90 **220**、最高 **29,145** |
| 截成 5 則後保留 | 約 13,841 則 = **3.6%** |
| 評論數超過 5 則（會被截斷）的商家 | **87.9%**（約 2,555 家） |

**87.9% 的商家會被截斷** —— 中位數 37 則代表一個典型商家有 7.4 倍的內容你看不到。

### 4.2 時間覆蓋：5 則只代表 7.6 週

在評論數 ≥ 20 則的 1,896 家商家中：

| 指標 | 數值 |
|---|---|
| 最新 5 則涵蓋的時間跨度（中位） | **53 天**（約 7.6 週） |
| 完整歷史涵蓋的時間跨度（中位） | **1,693 天**（約 4.6 年） |
| **時間覆蓋率** | **3.1%** |

一家開四年的店，你的頁面只呈現它最近七週的評價。

### 4.3 失真程度：整體平均看不出來，個體嚴重偏誤

| 指標 | 5 則平均 | 完整歷史平均 |
|---|---|---|
| 全體平均星等 | 4.726 | 4.782 |

整體只差 **0.056 星**，看起來無傷大雅。但拆到個體層級：

| 指標 | 數值 |
|---|---|
| 每商家平均絕對差 | **0.256 星** |
| 差 ≥ 0.5 星的商家 | **296 家 / 1,896 家 = 15.6%**（約六分之一） |
| 讀起來**偏高**的商家 | **1,027 家** |
| 讀起來**偏低**的商家 | **455 家** |

**關鍵洞察：偏誤方向不對稱且不可預測。**
1,027 家偏高 vs 455 家偏低 —— 多數商家的小幅偏高，被少數商家的大幅偏低拉低，掩蓋了整體平均的差異。對消費者來說：

> **這個網站不能讓人用評論數判斷一家店好不好，而且它系統性地偏樂觀。**

### 4.4 單一評論的破壞力

在 5 則的顯示視窗裡，一則新來的 1 星評論會擠掉原本的第 5 則：

| 被擠掉的原評論 | 5 則平均的變化 |
|---|---|
| 原本 5 星 | 4.8 → **4.0**（**−0.8 星**） |
| 原本 4 星 | 4.6 → **4.0**（**−0.6 星**） |
| 原本 1 星 | 不變 |

也就是說，**任意一位顧客的一次不愉快，就能讓這家店在你的頁面上看起來掉 0.6–0.8 星**。對商家來說是個真實的風險；對消費者來說，你給的星等其實是**滾動視窗裡的雜訊**。

### 4.5 還有 32.4% 根本沒有文字

**32.4% 的評論只有星等、沒有文字**（約 124,572 則）。這些評論無法被引用、無法被摘要、對使用者毫無資訊量 —— 但它們佔滿了你的 API 呼叫配額。

### 4.6 商用風險：顯示不全可能構成不實表示

這是**台灣消保法與公平交易法層面的風險**，常被忽略：

如果你在自己的網站上顯示 5 則評論，讓消費者以為「這是這家店的全部評價」，而實際上該店有 37 則評論（且其中 1,027 家的完整平均比顯示值高），這個呈現方式本身就有被主張為**廣告不實 / 誤導消費者的空間**。

**緩解做法**：
- 明確標註「以下顯示 Google 上最相關的 5 則評論，完整評論請見 Google Maps」
- 顯示評論總數與整體星等（但這需要 Places API 的 `rating` / `userRatingCount` 欄位，要另計 SKU）
- 永遠提供 `googleMapsUri` 直達原始頁面
- **絕對不要**自己動手把 5 則排版成「最新評論」或「所有評論」

## 5. 成本結構與單位經濟

### 5.1 計價基準（Google Maps Platform 官方定價，2026-10 核對）

**所有 SKU 採分級累進計價**：每個用量區間單獨計費後加總（例：10 萬次 Maps JS = 90,000 × $7 + 10,000 × $5.60 = $630 + $56 = $686）。

| SKU | 用途 | 免費額度／月 | 最低付費帶單價 |
|---|---|---|---|
| **Maps Embed API** | 嵌入地圖（iframe） | **無上限免費** | — |
| Maps JavaScript API | 互動式地圖 | 10,000 | **$7.00** / 1,000 |

### 5.2 單位經濟：核心的一個數字

| 項目 | 換算 | 說明 |
|---|---|---|
| 單次評論牆檢視 | $25 / 1,000 = **NT$0.785** | Place Details Ent+Atmosphere |
| 單次地圖載入 | $7 / 1,000 = **NT$0.220** | Maps JavaScript API |
| 單次頁面瀏覽的廣告收益 | NT$150 / 1,000 = **NT$0.150** | 淨 CPM 假設 |

> ### **一次評論牆檢視 = 5.2 次廣告曝光**
>
> ```
> NT$0.785 ÷ NT$0.150 = 5.23 倍
> ```
>
> **你每讓一個人看一次評論，就少賺了 5.2 個廣告版位的錢。**

這是整個商業模式的死結：**評論是這個產品裡最貴的部分（$25 vs $7，是地圖的 3.6 倍），卻是價值最低的部分** —— 因為它只有 5 則、3.6% 覆蓋率、32.4% 沒文字、而且 Google 自己就在同一個頁面上做得比你完整。

### 5.3 流量天花板：這門生意有上限，而且上限很低

在「純廣告 CPM NT$150、無固定成本、無訂閱收入」的假設下，計算利潤由正轉負的臨界流量：

| 技術組合 | **最大可承受月流量** |
|---|---|

**這張表是整份報告最重要的一張表。**

三個結論：

1. **秀評論會把天花板壓到 9,181 PV** —— 這是一個還沒長大就會壞掉的站。
2. **換地圖供應商救不了** —— Maps JS、Mapbox、Maps Embed 三者的天花板完全相同（9,181），因為瓶頸是評論 SKU，不是地圖。
3. **把評論拿掉，天花板立刻跳到 12 萬 – 44 萬 PV** —— 也就是說，**地圖不賺不賠，殺死這個網站的是評論**。

| 淨 CPM | 最大可承受流量 |

| NT$50 | 4,231 PV |

**要把天花板從 9,181 拉到 5 萬 PV 以上，CPM 得是 NT$300 —— 而台灣一般媒體網站的淨 RPM 是在下滑的**（前份報告：媒體網站 RPM 已從 US$30–50 跌到 US$12–22）。

**再加入訂閱與商家收入**：

| 情境 | 可獲利流量區間 |
|---|---|

## 6. 免費替代方案評估：能解地圖，解不了評論

## 7. 台灣法規接觸點

### 7.1 個人資料保護法（個資法）

**受影響的資料**：評論者姓名、頭像照片、造訪月份（`visitDate`）、造訪次數、發文時間、個人檔案連結。

| 要求 | 說明 |
|---|---|
| 蒐集特定目的 | 你蒐集這些資料的目的必須明確（例：展示該商家評價） |
| 告知義務 | 隱私權政策需說明**第三方內容來源**（來自 Google Maps Platform API） |
| 個資法 §8–§10 | 利用個人資料須符合特定目的與方法 |

實務上多數業者援引「Google 公開 UGC 政策」主張資料已公開可用，但**這是需要法律評估的論點，不是自動成立的安全港**。

### 7.2 著作權法

**評論是評論者的著作**（言論著作 / 文字著作）。
- API 授權涵蓋的是「**顯示**」，**不涵蓋「轉售資料」**。
- 系統性抓取建庫 → 觸及著作權法第 91 條的**重製權**與**散布權**。
- 若將評論內容用於 AI 訓練或做成衍生資料集，風險再升高。

### 7.3 商標法與 Google 品牌規範

- 使用 Google Maps 標誌、紅色 pin、「Google Maps」字樣，必須依 **Google 品牌規範**（Brand Permissions）處理。
- **不得讓自己的頁面看起來像是 Google Maps 官方頁面** —— 混淆式介面同時觸發商標法與公平交易法。

### 7.4 公平交易法與消費者保護法

- **廣告不實 / 誤導**：只顯示 5 則評論卻暗示是完整評價（見第 4.6 節）。
- **不公平交易行為**：以自己是「地圖 + 評論平台」招徠，卻未揭露資料來自 Google。

### 7.5 台灣適用的 Google 條款特殊點

- **EEA 專屬限制（2025-07-08 生效）不適用台灣**；但 billing address 若在 EEA 則適用。
- 台灣的 Google Maps Platform 用量計價與美元報價相同，**沒有本地幣別報價**。

## 8. 商業模式評估（5 個模型）

### 模型 A —— 單一商家自我評論展示 ⭐ 推薦

| 項目 | 內容 |
|---|---|
| **做法** | 每家商家一個頁面，顯示該商家自己的地圖與評論 |
| **資料來源** | **Business Profile API**（可取自己名下地點的**全部**評論，且可直接回覆） |
| **API 成本** | **NT$0**（Business Profile API 對已註冊商家免費） |
| **審核門檻** | 商家檔案已驗證且啟用 **≥ 60 天**、需有網站；**審批通過前 quota = 0 QPM** |
| **收費** | 建置 NT$3,000–15,000／站 + 月費 NT$500–3,000 |
| **損益試算** | 20 客戶 × NT$3,000/月 = **NT$60,000/月**，扣主機 NT$3,000 → 淨 **NT$57,000**（未計人力） |
| **合規風險** | **最低** —— 資料來自商家自己的 Business Profile，Google 明確授權 |
| **護城河** | 中等 —— 靠服務品質與客戶關係，不是靠資料 |
| **評分** | ⭐⭐⭐⭐⭐ |

**為什麼這是最佳起點**：它是唯一一個 **API 成本為零**、**法遵乾淨**、**收入結構簡單**、**不需要流量**的模型。AI 草擬回覆、負評即時警示、SERP 星等追蹤都是真正的價值。

### 模型 B —— 產業目錄 / 找店平台

| 項目 | 內容 |
|---|---|
| **做法** | 抓（或查）某一產業的商家，列出清單 + 地圖 + 評論 |
| **技術可行性** | ✅ 高 |
| **條款判定** | ❌ **條款 3.2.3(d) 明文禁止建立 listings or directory service** |
| **經濟判定** | ❌ **流量天花板 9,181 PV，廣告模式在數學上無解** |
| **評分** | ⭐☆☆☆☆ **不建議** |

**如果非做不可怎麼改造**：把「目錄」改成「**評鑑內容**」——
- 你的主體是**你寫的評測、排行、教學**（原創內容）
- 地圖與評論是**佐證引用**（每次即時請求、標 Google 歸屬、不快取）
- 收入來自你的內容價值，不靠複製 Google 的內容
- 實測流量若無法超過 9,181 PV 就必須調整，否則這條路仍然走不通

## 9. 灰色地帶：可行性與期望值

> 以下四個模型均**違反 Google 條款**，且多數同時涉及台灣法規問題。本節的用途是**量化風險**以支持「不要做」的決策，不是提供操作指引。

### 9.1 期望值框架

```
EV = (1 − P) × T×C − P × L
臨界機率 P* = T×C ÷ L
```

- **T×C** = 期望情況下的月淨利（營收 − 成本）
- **P** = 被查機率（Google 處置 + 法遵追訴 + 客戶流失的合併機率）
- **L** = 一旦被查的總損失（重建成本 + 商譽 + 訴訟 / 和解 + 帳號停權）

**判準：若 P > P\*，期望值為負，不該做。**

### 9.2 四個灰色模型

**GM-1　爬蟲建庫（自建商家 + 評論資料庫）**

| 項目 | 數值 |
|---|---|
| 月營收 | 廣告 NT$30,000（20 萬 PV）+ 30 商家 × NT$1,500 上架費 = NT$75,000 |
| 月成本 | 主機 + 代理 + 開發攤銷 = NT$25,000 |
| **T×C** | **NT$50,000** |
| 被查機率 P | **30%**（條款明文違規 + Google 對 scraper 有實際訴訟紀錄） |
| 損失 L | NT$800,000（資料重建 NT$600,000 + 商譽 + 律師 / 和解） |
| **臨界機率 P\*** | **6.25%** |
| **EV** | **NT$−205,000**（EV/(T×C) = **−4.10**） |

**GM-2　洗評 / 轉售評論**

| 項目 | 數值 |
|---|---|
| 月營收 | 800 則 × NT$150 毛利 = NT$120,000 |
| **T×C** | **NT$120,000** |
| 被查機率 P | **55%**（Google 主動偵測 + 商家端被檢舉 + 多國消保機關對 fake review 執法） |
| 損失 L | NT$2,000,000（刑事風險 + 客戶集體求償 + 名譽） |
| **臨界機率 P\*** | **6.00%** |
| **EV** | **NT$−1,046,000**（EV/(T×C) = **−8.72**） |

**GM-3　混淆式介面（讓自己的頁面看起來像 Google Maps）**

| 項目 | 數值 |
|---|---|
| **T×C** | **NT$50,000** |
| 被查機率 P | **25%** |
| 損失 L | NT$500,000（商標 / 公平交易命令 + 停權 + 律師） |
| **臨界機率 P\*** | **10.00%** |
| **EV** | **NT$−87,500**（EV/(T×C) = **−1.75**） |

**GM-4　繞過 5 則上限做聲譽分析 SaaS**

| 項目 | 數值 |
|---|---|
| **T×C** | **NT$40,000**（20 客戶 × NT$3,000/月） |
| 被查機率 P | **35%** |
| 損失 L | NT$600,000 |
| **臨界機率 P\*** | **6.67%** |
| **EV** | **NT$−184,000**（EV/(T×C) = **−4.60**） |

### 9.3 規模敏感度：期望值隨規模遞減

以 GM-1 為例：

| 規模 | T×C | P | L | **EV** | EV/(T×C) |
|---|---|---|---|---|---|
| 1 倍 | NT$50,000 | 30% | NT$800,000 | **NT$−205,000** | **−4.10** |
| 3 倍 | NT$150,000 | 45% | NT$2,400,000 | **NT$−997,500** | **−6.65** |
| 10 倍 | NT$500,000 | 60% | NT$8,000,000 | **NT$−4,600,000** | **−9.20** |

**這個結構和前一份報告的結論完全一致：**
收益與被查機率同向增長，但**損失超線性增長**（資料庫被扣押 = 全損、追訴範圍擴大、客戶集體求償）。**規模一大就崩壞。**

四個模型的 **P\*** 全部落在 **6.00% – 10.00%** 的極低區間 —— 意思是：**這個生意在「幾乎不可能被查到」的假設下才勉强能成立**。而它偏偏是條款寫明禁止、且 Google 有實際执法紀錄的行為。

### 9.4 灰色 → 合法的對照表

| 灰色做法 | 它背後的真實需求 | **合法版本** |
|---|---|---|
| 爬蟲建商家庫 | 想有資料資產 | Business Profile API（管自己的店）＋ 合法授權的第三方資料商 |
| 繞過 5 則上限 | 想看完整評論 | Business Profile API（自己的店可拿全部） |
| 洗評 | 商家想提高排名 | 鼓勵商家用促換 / 優惠換取誠實評論；做提醒與回覆後台（C 模式） |
| 混淆式介面 | 想讓人信任 | 清楚標示「本頁評論資料來自 Google Maps」，提供原始連結 |
| 隱藏 Google 歸屬 | 想省版面 | 用 Places UI Kit（Google 官方提供的合規元件） |
| 假設評論資料自己建的 | 想做分析 | Business Profile API 自己的店 + 商家提供的第一手資料 |

### 13.4 Business Profile API 對照

| 面向 | Places API | Business Profile API |
|---|---|---|
| 能取的評論 | **最多 5 則** | **自己名下地點的全部**（分頁） |
| 能否回覆 | ❌ | ✅ |
| 審批 | 無 | **需審批 + 檔案啟用 ≥60 天 + 有網站；審批前 quota = 0** |
| 費用 | 依 SKU 計費 | 已註冊商家免費 |
| 對象 | 任何商家 | **只有你自己管理的商家** |

### 13.5 常見實作陷阱

| 陷阱 | 後果 | 正確做法 |
|---|---|---|
| 用 Selenium 爬 Google Maps 拿評論 | 違反 3.2.3(a)(b) + 個資法 + 著作權法 | 用 API；自己的店用 BP API |
| 把評論快取成自己的資料庫 | 違反 3.2.3(b) | 只永久存 `place_id`；經緯度 30 天；評論即時請求 |
| 以為付更多錢可以買更多評論 | 不存在此 SKU | 5 則是硬上限 |
| 以為排序選項能拿到「最新 5 則」 | 拿到的是「5 則的最新排列」 | 若要真正的最新，需要商家自有資料（BP API） |
| 只顯示星等不顯示文字來源 | 32.4% 的評論沒有文字 | 標示「此評論僅有星等評分」 |
| 隱藏 Google 歸屬或改樣式 | 違反 Places API Policies | 原樣呈現 |
| 以為 field mask 不影響費用 | SKU 由欄位決定 | 用最少欄位達到目的 |
| 忘記開預算警示 | 一夜之間帳單爆炸 | 設預算 + 每日呼叫量監控 |
