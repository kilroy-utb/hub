地圖 + Google 評論，到底做不做？

你問的兩件事 —— 地圖可以撈、Google 評論可以秀 —— 技術上都做得到。 真正的問題不是能不能做，而是做完之後能不能賺錢、會不會被 Google 關掉。 這份報告把條款紅線、評論 5 則上限的真實影響、API 成本結構與灰色地帶期望值全部量化。

Executive Summary

一句話結論

做得出來，但賺不到錢
技術可行性 ≈ 90%　|　商業可行性（做成公開目錄）≈ 極低　|　推薦路徑：服務單一商家
秀評論這件事會把你的網站流量天花板壓到 9,181 PV／月。 超過這個數，每多一個訪客就多虧一筆錢 —— 因為 Google 條款禁止快取，成本無法攤平。 把評論拿掉，同一個網站的天花板立刻跳到 12 萬 – 44 萬 PV。

① 地圖可以撈嗎？

✅ 可以

Maps Embed API 免費無上限；Maps JavaScript API $7／1,000（免費額 1 萬）。 但「撈」只能是單次即時呼叫，不能變成你的資料庫。

批次抓全台商家存檔 → 違反條款 3.2.3(a)(b)

② 評論可以秀嗎？

⚠️ 可以，但有硬上限

Place Details Ent+Atmosphere $25／1,000。每家最多 5 則， 依相關性排序，無分頁、無 token、付更多錢也解鎖不了。

另有一整包強制呈現義務（姓名、照片、歸屬、回報…）

③ 這樣能賺錢嗎？

❌ 做成公開目錄：不行

條款 3.2.3(d) 明文禁止用 Maps Core Services 建立 「listings or directory service」。這不是灰色地帶，是紅線。

✅ 服務單一商家（BP API）：API 成本 NT$0

④ 換免費方案有救嗎？

⚠️ 地圖有救，評論無解

MapLibre + OpenFreeMap 地圖端 $0；OSM（ODbL）可合法自建目錄， 繞開 3.2.3(d)。但評論無替代。

✅ Yelp Enhanced + 24h 快取 → 天花板 145,110 PV

六個核心結論

01

技術可行性 ≈ 90%，1–2 天可做出原型

Google 官方範例本身就能跑。阻擋你的從來不是工程能力。

02

真正的一刀切在條款 3.2.3(d)

「商家列表或目錄服務」被直接點名禁止。安全港只有一個： substantial, independent value（實質且獨立的價值）。

03

5 則上限是模型的致命傷

只保留 3.6% 語料、87.9% 商家被截斷、32.4% 評論沒有文字、 時間覆蓋率只有 3.1%。但整體平均星等只差 0.056 —— 偏誤藏在個體裡。

04

經濟結構是「越紅越虧」

一次評論牆檢視成本 NT$0.785，是單次廣告收益 NT$0.150 的 5.23 倍。而且有明確天花板。

05

灰色地帶期望值全負，且隨規模遞減

4 個灰色模型臨界機率 P* 落在 6.00% – 10.00%， 實際被查機率 25% – 55%。規模 1 倍 → 10 倍，EV/(T×C) 從 −4.10 惡化到 −9.20。

06

免費替代方案能解地圖，解不了評論

MapLibre + OpenFreeMap 讓地圖端 $0，OSM 讓你合法自建目錄； 但評論只能靠 Yelp Enhanced（$299/月、3 則 ×160 字元）。 關鍵是快取權不是價格：Yelp 24h 快取讓成本 ∝ 商家數，天花板從 9,181 解到 145,110 PV（高 15.8 倍）。

需求拆解

「撈」的三個層級，合法性完全不同

「有地圖可以撈」這句話裡，其實混了三件差異很大的事。

層級做法技術可行條款判定說明
L1 顯示嵌入 Google 地圖 iframe 或用 Maps JS API✅合規Maps Embed API 免費無上限；Maps JS API 有免費額度
L2 查詢用 Places API 搜附近商家、取名稱地址星等✅有條件合規必須即時呼叫、標 Google 歸屬、不得改寫
L3 蒐集批次抓全台商家、存成自己的資料庫✅ 技術上做得到明文禁止No Caching + No Scraping（3.2.3a、3.2.3b）

L3 為什麼不行 —— 三道具體限制

No Scraping（3.2.3a）

不得預先抓取、索引、儲存、轉發或重新託管 Maps Content。 明文包含複製儲存使用者評論。

預先跑一輪把資料灌進自己的庫 —— 正中此條。

No Caching（3.2.3b）

不得快取。Places API 唯一豁免是 place_id 可永久儲存； 經緯度僅可暫存 30 天；評論不在豁免清單。

→ 成本無法攤平、沒有資料庫、沒有 SEO 資產、沒有護城河。

搜尋本身也沒有「全部」

Text Search：每頁 20 筆、單次最多 60 筆。Nearby Search：每次最多 20 筆。

Nearby Search 沒有「只要 ID」的 SKU —— 即使只想拿 place_id 過水，一樣按 $32／1,000 計費。

「Google 評論可以秀」的三個硬條件

條件一：只有 5 則，而且付更多錢也解鎖不了

Places API (New) 的 Place Details 回傳評論時，最多 5 則，依相關性排序。 沒有分頁參數、沒有 pageToken、沒有排序選項。Legacy Place Details 雖提供 most_relevant / newest 排序選項，但回傳筆數上限同樣是 5 則。 Google 官方文件明載：沒有任何付費方案可以解鎖更高的上限。

實作陷阱：若你要「最新優先」，做法是取回那 5 則（相關性排序）後在本地用 publishTime 排序。 但那得到的是「5 則的最新排列」，不是「最新的 5 則」。這個差別在下一章會變成一個真實的商業問題。
條件二：要買對 SKU（你的費用取決於你問了什麼）

含評論需要 Place Details Enterprise + Atmosphere（$25／1,000，超過 1,000 次免費額度後）。 如果 field mask 只要 rating 或 reviews 以外的欄位，會被歸到不同計價級距。

Places API 的費用取決於 field mask（你要求了哪些欄位），不是取決於你「用在哪裡」。 多要一個 photos 欄位，可能就跳到不同的 SKU 級距。

條件三：八項強制呈現義務，漏一項就違規
義務具體要求
顯示作者資訊姓名 + 照片 + 個人檔案連結（空間有限時照片至少要顯示）
導向原始來源提供 googleMapsUri 直達 Google Maps 原始評論
歸屬顯示 Google logo 或「Google Maps」字樣，且不得修改外觀
說明排序必須說明評論的排序／篩選方式（預設為相關性）
回報機制提供 flagContentUri 回報連結
時間標示建議顯示 relativePublishTimeDescription
翻譯揭露若做了翻譯，必須告知並提供 originalText 原文

✅ 可以合法加值：AI 摘要 reviewSummary —— 但必須逐字顯示 disclosureText、標題固定用「Review summary」、附上 Google 說明連結與回報連結。

一個容易被忽略的技術限制：Places API (New) 不回傳商家回覆（owner response），也不回傳評論照片。 第三方「評論牆」產品的常見功能，API 層級其實給不了。
Google Maps Platform 條款 3.2.3

三道紅線（其中一道直接命中）

3.2.3 (a)

No Scraping —— 禁止抓取

不得預先抓取、索引、儲存、轉發或重新託管 Maps Content。 明文包含複製儲存商家名稱、地址、使用者評論。

命中：任何「先跑一次程式把全台商家與評論抓回來存進 MySQL / Airtable / BigQuery」的設計。
3.2.3 (b)

No Caching —— 禁止快取

不得快取 Google Maps Content。Places API 的唯一豁免是 place_id 可永久儲存；經緯度可暫存 30 天；評論不在豁免範圍。

這一條直接決定了本生意 的經濟結構：成本 = 流量 × 單位成本，嚴格線性，無法攤薄。
3.2.3 (c)

No Creating Content From Maps Content

不得用 Places API 的經緯度做 point-in-polygon 分析。 EEA 版本另禁止用 Maps Content 訓練或測試 AI 模型。

命中：想做「找出某服務範圍內的所有店」這種分析，用 Places API 資料做就是違規。
3.2.3 (d) ⭐ 最致命

No Re-Creating Google Products / No Directory Service

不得使用 Services 建立與 Google 產品功能實質相似的產品。 明文禁止使用 Maps Core Services 建立 listings or directory service（商家列表或目錄服務）， 也禁止用它建立或擴充廣告產品。產品必須有 substantial, independent value。

直接命中：你想做的「找店平台」，在條款裡的正式名稱就叫「目錄服務」。 這不是灰色地帶，是紅線。

唯一安全港：substantial, independent value 測試

檢驗面向✅ 會通過❌ 不會通過
資料層地圖與評論只是佐證引用，核心價值在你的後端網站主體就是「地圖 + 評論列表」
流量來源你的原創內容（評測、教學、排行分析）帶來流量靠 Google 的資料內容本身吸引流量
資料所有核心資料是你自己產生或合法授權的核心資料就是 Google 的商家與評論
呈現方式即時請求、標 Google 歸屬、不改寫快取成自己的庫、自建「評論資料庫」
EEA 專屬限制（2025-07-08 生效）：Places API 內容不得再與任何地圖（包括 Google Map）並列顯示， 須改用 Places UI Kit。台灣不在 EEA，此條不適用；但若你的 Google Cloud billing address 在 EEA，則該限制會適用到你的專案。

對消費者：這個網站不能讓人用評論數判斷一家店好不好，而且它系統性地偏樂觀。

單一評論的破壞力

在 5 則的顯示視窗裡，一則新來的 1 星評論會擠掉原本的第 5 則：

被擠掉的原評論5 則平均的變化
原本 5 星4.8 → 4.0（−0.8 星）
原本 4 星4.6 → 4.0（−0.6 星）
原本 1 星不變
任意一位顧客的一次不愉快，就能讓這家店在你的頁面上看起來掉 0.6–0.8 星。 對商家是真實風險；對消費者，你給的星等其實是滾動視窗裡的雜訊。

商用風險：顯示不全可能構成不實表示

如果你在自己的網站顯示 5 則評論，讓消費者以為「這是這家店的全部評價」， 而實際上該店有 37 則評論（且其中 1,027 家的完整平均比顯示值高）， 這個呈現方式本身就有被主張為廣告不實 ／ 誤導消費者的空間（消保法、公平交易法）。

緩解做法

  • 明確標註「以下顯示 Google 上最相關的 5 則評論，完整評論請見 Google Maps」
  • 顯示評論總數與整體星等（需 Places API 的 rating / userRatingCount 欄位，要另計 SKU）
  • 永遠提供 googleMapsUri 直達原始頁面
  • 絕對不要自己動手把 5 則排版成「最新評論」或「所有評論」

台灣法規接觸點

個人資料保護法

受影響資料：評論者姓名、頭像、造訪月份（visitDate）、造訪次數、發文時間、個人檔案連結。

須有特定目的、告知義務（隱私權政策需說明第三方內容來源 = Google Maps Platform API）。 實務上多數業者援引「Google 公開 UGC 政策」，但這是需要法律評估的論點，不是自動成立的安全港。

著作權法

評論是評論者的著作（言論著作／文字著作）。 API 授權涵蓋的是「顯示」，不涵蓋「轉售資料」。

系統性抓取建庫 → 觸及著作權法第 91 條的重製權與散布權。 若把評論用於 AI 訓練或做成衍生資料集，風險再升高。

商標法與 Google 品牌規範

使用 Google Maps 標誌、紅色 pin、「Google Maps」字樣，必須依 Google Brand Permissions 處理。

不得讓自己的頁面看起來像是 Google Maps 官方頁面 —— 混淆式介面同時觸發商標法與公平交易法。

公平交易法與消保法

廣告不實／誤導：只顯示 5 則評論卻暗示是完整評價（見第 4.6 節）。

不公平交易行為：以自己是「地圖＋評論平台」招徠，卻未揭露資料來自 Google。

Places API (New) 取得評論的請求範例

GET https://places.googleapis.com/v1/places/{PLACE_ID}
     ?key={API_KEY}
     &fields=id,displayName,formattedAddress,location,rating,userRatingCount,
             googleMapsUri,reviews,reviewSummary

欄位取捨決定費用：要求 reviewSummary 與 reviews 會進入 Enterprise + Atmosphere 級距（$25／1,000）。

呈現義務檢查表（每個頁面都要過）

  • 作者姓名
  • 作者照片（空間有限也要顯示）
  • 作者個人檔案連結
  • googleMapsUri 直達原始評論
  • Google logo ／「Google Maps」歸屬，樣式未被修改
  • 說明評論排序方式（預設相關性）
  • flagContentUri 回報連結
  • relativePublishTimeDescription 時間標示
  • 若翻譯 → 告知使用者 ＋ 提供 originalText
  • 說明 Google 如何驗證評論
  • 若用 reviewSummary → 逐字顯示 disclosureText、標題「Review summary」、附說明與回報連結
  • 明確標示「顯示最相關的 5 則」並提供完整評論原始連結

常見實作陷阱

陷阱後果正確做法
用 Selenium 爬 Google Maps 拿評論違反 3.2.3(a)(b) ＋ 個資法 ＋ 著作權法用 API；自己的店用 BP API
把評論快取成自己的資料庫違反 3.2.3(b)只永久存 place_id；經緯度 30 天；評論即時請求
以為付更多錢可以買更多評論不存在此 SKU5 則是硬上限
以為排序選項能拿到「最新 5 則」拿到的是「5 則的最新排列」要真正的最新，需商家自有資料（BP API）
只顯示星等不顯示文字來源32.4% 的評論沒有文字標示「此評論僅有星等評分」
隱藏 Google 歸屬或改樣式違反 Places API Policies原樣呈現
以為 field mask 不影響費用SKU 由欄位決定用最少欄位達到目的
忘記開預算警示一夜之間帳單爆炸設預算 ＋ 每日呼叫量監控
