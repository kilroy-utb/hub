# Project-Oriented Multi-Agent Workflow（可重用 SOP）

> 本文件為 **agent 可遵循的標準作業程序**。任何 agent 團隊（主 agent + sub agent）都可依此執行一個「研究／產出」型專案。
>
> 來源：由一次真實模擬（2026 美國期中選舉對馬斯克的影響研究）萃取而成，含該次執行暴露的失效模式與對應防護。
> 情境式交付物在 `/workspace/projects/<專案代號>/`，本檔在 `/workspace/AGENT_WORKFLOW.md`。

---

## 0. 核心原則（違反即流程失效）

1. **單一事實來源（Single Source of Truth）**：spec 是唯一裁定基準。sub agent 一律以 spec 為準，衝突時 spec 勝出。
2. **關卡不可跳過**：Gate 1（需求意圖）、Gate 2（規格核准）必須由需求者拍板。sub agent **絕不可**代需求者決定。
3. **審查是硬性回退，不是建議**：review 判定不通過，必須回到對應的前一 pipe 重作，而非「提醒注意」。
4. **每個 pipe 都要有退出條件**：沒有 exit criteria 就無法判斷該放行還是回退。
5. **缺失要明寫，不得腦補**：查不到就寫「查無資料」並說明原因。禁止用同類事件、歷史類比或合理化敘述填空。
6. **全程 append-only 紀錄**：每個 pipe 的輸入、輸出、verdict、重試次數、回退決策都要留痕。

## 1. 角色定義

| 角色 | 定位 | 職責 | 不可做 |
|---|---|---|---|
| **#1 Planner**（主 agent） | 專案負責人 | 規劃、拆 shard、派工、寫 spec、裁決、交付、確保紀錄完整 | 不得代需求者做需求決定 |
| **#2 Reviewer**（sub agent） | 獨立稽核者 | 需求審 → 研究審 → 文件審；發回不合格項 | 不得自行修改產物、不得代需求者決定 |
| **#3 Researcher**（sub agent） | 取證者 | 依 spec 上網蒐集事實與素材 | 不得推論未發生之事、不得超出 spec 範圍 |
| **#4 Document maker**（sub agent） | 產出者 | 依 spec + 已核准研究筆記產出文件 | 不得自行上網補資料、不得發明內容 |

### 1.1 Planner 的五項核心責任

1. **交付物定義** — 明確檔名、格式、語言、量化表要求
2. **模型配對** — 依角色特質指派模型（見 §9）
3. **Fork 排程** — 決定何時 fork 幾個 sub agent、平行度、並行槽位管理
4. **網路蒐集範圍界定** — 什麼要查、查多深、引用截止時點為何
5. **Reviewer 審查項目定義** — 每個 gate 要檢查什麼寫進 spec 審查基準

### 1.2 Reviewer 為何必須獨立

Reviewer 是唯一有權「發回」的節點。三道防護缺一不可：

- **角色隔離** — Reviewer 不參與研究與撰寫
- **清單式審查** — 審查項目事先寫死在 spec，不是臨場發揮
- **結構化輸出** — 禁止「整體看起來不錯」這種無效回饋

若環境不支援模型覆寫（見 §9.2），角色隔離與清單式審查就是防止橡皮章的唯一手段，**必須執行到位**。

## 2. 管線總覽

| Pipe | 擁有者 | 動作 | 產出 | 退出條件 |
|---|---|---|---|---|
| **0** | #1 | 建立專案骨架與紀錄檔 | 目錄 + `PIPELINE_LOG.md` | 目錄與模板就位 |
| **1.1** | #1 + 需求者 | 確認需求（**Gate 1**） | `01-requirements.md` | 需求者確認意圖無誤 |
| **1.2** | #2 | 問答式需求審查 | `02-review-requirements.md` | VERDICT PASS 且無高嚴重度 finding |
| **1.3** | #1 | 撰寫 spec | `00-spec.md` | spec 覆蓋全部已定案決策 |
| **1.4** | 需求者 | 核准 spec（**Gate 2**） | spec 凍結 | 需求者核准，狀態改為 FROZEN |
| **2.1** | #1 | fork 研究 shard | agent 指派明細寫入 log | shard 數與維度對應表一致 |
| **2.2** | #3 | 平行蒐集 | `10-research-S*.md` | 每個 shard 具備編號發現 + 查無資料清單 |
| **2.3** | #2 | 審查研究 | `20-review-research.md` | VERDICT PASS；否則回 2.2 |
| **3.1** | #1 | fork 文件 agent，附 spec + 已核准語料 | 派工紀錄 | 交付素材齊備 |
| **3.2** | #4 | 產出文件 | `30-document.md` / `.html` | 章節序與 spec 一致、全文可回溯 |
| **3.3** | #2 | 審查文件 | `40-review-document.md` | VERDICT PASS；否則回 3.2 |
| **4.1** | #1 + #2 | 最終確認，決定是否回退 | 回退決策 | 判定通過或指定回退點 |
| **4.2** | #1 | 通知需求者完成 | 交付連結 + 審查摘要 | 需求者收到 |
| **4.3** | #1 | 補齊紀錄 | `PIPELINE_LOG.md` 完整 | 每 pipe 皆有紀錄 |

### 2.1 迭代上限與升級

- 同一 pipe 最多 **3 輪**
- 第 3 輪仍不通過 → 升級為需求者決策（決策 pack），由需求者選擇：**放寬標準 / 修改需求（升版 spec）/ 停案**
- 研究審不通過 → 回 Pipe2.2（補蒐集）
- 文件審不通過 → 回 Pipe3.2（重寫文件）

### 2.2 回退原則

回退以「回到最近一次需求者核准版本」為準，**不重開 Gate 1**。spec 凍結後的變更一律升版（V1.0.1 → V1.0.2），並重新經需求者核准。

## 3. 檔案與目錄慣例

```
/workspace/projects/<專案代號>/
├── 00-spec.md                    # 單一事實來源（Gate 2 後 FROZEN）
├── 01-requirements.md            # 需求草案 + 需求者回覆紀錄
├── 02-review-requirements.md     # Reviewer 需求審查
├── 10-research-S1.md … S*.md     # 研究 shard 筆記
├── 20-review-research.md         # Reviewer 研究審查
├── 30-document.md                # 主交付
├── 30-document.html              # 次交付
├── 40-review-document.md         # Reviewer 文件審查
└── PIPELINE_LOG.md               # append-only 唯一 audit trail
```

**命名規則**：檔名前綴代表 pipe 階段（`0x` 規劃／`1x` 需求／`2x` 研究／`3x` 文件／`4x` 終審），流水號管線內唯一。`PIPELINE_LOG.md` 為全案唯一例外。

**紀錄檔表格格式**：

| Pipe | 時間 (UTC) | 擁有者 | 輸入 | 產出 | 狀態 |
|---|---|---|---|---|---|
| 1.1 | 2026-11-04 09:20 | #1 Planner | 需求者請求 | `01-requirements.md` | DONE |

狀態值固定用：`DONE` / `IN PROGRESS` / `FIX → 需需求者拍板` / `待 Gate N` / `BLOCKED`。**不要留下過期的 IN PROGRESS**。

## 4. Gate 機制（與宿主對話協定的格式契約）

Gate 是需求者拍板的關卡。**每則 Gate 訊息都必須以 options block 結尾**，否則宿主會視為回合結束。

### Gate 1（需求意圖）

```options
{"type":"approval","stage":"gate_1_requirements","required":true,"prompt":"Does this accurately reflect my intent?","choices":[{"id":"confirm","label":"Looks good, continue","default":true}]}
```

### Gate 2（規格核准）

```options
{"type":"approval","stage":"gate_2_spec","required":true,"version":"V1.0.0","prompt":"Is this specification approved for implementation?","choices":[{"id":"approve","label":"Approve and start implementation","default":true}]}
```

### 決策包（多題選單）

```options
{"type":"decision_pack","stage":"discovery","required":true,"choices":[],"prompt":"Select one option from each group","questions":[{"id":"1","prompt":"Target setup","choices":[{"id":"A","label":"Desktop browser (recommended)","default":true},{"id":"B","label":"Mobile"}]}]}
```

**格式契約（機讀，勿改）**：頂層 `choices` 陣列留空，真選項放 `questions`；`questions[].id` 必須是**數字**；`questions[].choices[].id` 必須是**單一英文字母**；`type` / `stage` / `id` / `label` 等鍵名保持英文原文；`prompt` 與 `label` 使用與周遭訊息相同的語言。

### 注意事項

- 一則訊息最多問 3 題為佳；題數過多時改用兩階段。
- 每題都要給**具體可執行的預設答案**，使用者才可能一鍵決定。
- 提問前先用散文把背景講清楚，options block 裡只留標籤。
- 交付完成後若無待決事項，**不要**再附 options block。

## 5. Reviewer 審查契約

所有審查輸出格式固定，**不可改寫成敘述性意見**：

```
VERDICT: PASS | FIX | FAIL
FINDINGS:
[F-1] 嚴重度(高/中/低) | 問題描述 | 建議處置 | 定位:檔案:行號
QUESTIONS:            ← 僅需求審查階段使用
[Q-1] 問題 | 為何要問（會改變什麼） | 建議預設答案
```

**規則**：

1. `VERDICT` 必須是單獨一行，置於輸出最上方。
2. 每個 finding 都要有**精確定位**（`檔案:行號`），否則 owner 無法處置。
3. Finding 聚焦「會導致研究失敗或返工」的問題，不要列格式小建議。
4. Reviewer 不得修改被審查的產物，只能提要求。
5. 需求審查時，`QUESTIONS` 是主要產出——把模糊處挑出來交需求者拍板，而不是自己決定。

## 6. Researcher 取證規範

### 6.1 四級證據標籤（強制）

| 標籤 | 定義 | 附加要求 |
|---|---|---|
| `已證實` | 有具名來源直接支持 | 附 URL + 存取日期 |
| `合理推估` | 由已證實事實合理外推 | 附依據來源 + 方向 + 不確定度（高／中／低） |
| `情境假設` | 假設性推演，無直接證據 | 標明前提與不可驗證性 |
| `查無資料` | 原理上或實務上查不到 | 說明原因；**不得用同類事件代替** |

### 6.2 硬性規則

1. **引用截止時點** — spec 必須指定一個截止時刻，之後的資訊一律不得引用。
2. **禁精確數字預測** — 不得預測股價漲跌幅、合約金額等未發生的數字。**但已發生的歷史數據可以且必須查實**（量化表需要）。
3. **一手來源優先** — 官方選務機構、法條與政府公告、公司財報與 10-K、SEC 文件、法院文件、機關公告；二手媒體僅供交叉驗證，並須區分「事實報導」與「評論／預測」。
4. **矛盾不取捨** — 找到互相矛盾的來源時**兩者都記錄**並標明矛盾點。
5. **編號穩定** — 每條發現給 `S<n>-#<N>` 連續編號，文件端據此引用，編號一旦發布不得重編。
6. **查無資料清單** — 每個 shard 結尾必附：查了什麼、為何查不到。
7. **自評段** — shard 結尾誠實列出哪些要求項目只部分完成、哪些可能有誤，供 Reviewer 判斷是否補蒐集。

### 6.3 產出結構模板

```markdown
# S<n> 研究筆記：<主題>
> 對應 spec：<維度／層次>。依據 00-spec.md v1.0.0（FROZEN）。引用截止時點：<時點>。

## 0. 查詢紀錄            ← 搜尋關鍵字與來源網域，讓審查者能重現
## 1. 核心發現            ← S<n>-#N 連續編號，每條附來源與標籤
## 2. …（依維度分節）
## 6. 查無資料清單
## 7. 限制與不確定性
## 8. 自評
```

## 7. Document maker 規格

1. **只用已核准的研究筆記** — 引用時標註 shard 與編號（如 `S3-#4`）。
2. **不得自行上網補齊** — 研究筆記未覆蓋者寫「查無資料」並列入附錄。
3. **全文可回溯** — 每一條陳述都要能對回某個研究筆記編號。
4. **章節序由 spec 固定** — 文件端不得自創章節或調整順序。
5. **多格式必須同源** — HTML 版由 Markdown 版轉換而來，內容一致，不得額外發明。
6. **美觀屬於審查項目** — 表格可讀性、層級、術語一致、無錯字、無殘留佔位符，都算審查基準。

## 8. Spec 撰寫清單（Planner 必備）

一份合格的 spec 至少包含：

1. **研究命題** — 一句話寫清楚要回答什麼問題
2. **因果方向** — 明確寫出，避免下游各自發揮
3. **前提的操作性定義** — 量化門檻、可驗證的成立條件
4. **引用截止時點**
5. **語言、格式、交付清單、量化表要求**
6. **時間跨度** — 基線期 / 聚焦期 / 歷史對照
7. **事實處理原則** — 證據標籤、禁止事項、混淆因素切割線
8. **維度表** — 每個維度寫清「涵蓋內容」與「要回答的關鍵問題」
9. **每維度的撰寫結構**（例如四欄：影響內容／反饋反制／時程／歸因強度）
10. **研究分片對應表** — shard → 維度 → 主題 → 產出檔名
11. **研究端取證規範與禁止事項**
12. **文件端章節序與審查基準**
13. **流程治理** — 審查契約、迭代上限、變更與回退規則、紀錄要求
14. **已知風險與限制** — 隨 spec 一併凍結，避免下游踩雷

## 9. 模型指派與 Fork 策略

### 9.1 理想配對

| 角色 | 特質需求 | 建議層級 |
|---|---|---|
| #1 Planner | 全局判斷、拆解、協調 | 最強推理模型 |
| #2 Reviewer | 嚴謹、不被說服 | 最強推理模型（推理強度調高） |
| #3 Researcher | 大量取證、可平行 | 快模型，成本敏感 |
| #4 Document maker | 排版與文筆 | 中等成本，重文筆 |

### 9.2 環境限制與退路（實測必讀）

`spawn_agent` 的 `model` 參數**不一定被 runtime 支援**。實測可能回傳：

```
invalid params, unknown model 'gpt-5.6-sol' (2013)
```

**退路**：省略 `model` 參數，sub agent 繼承主模型。此時：

- 「用不同模型避免 reviewer 與作者同質化」的防護失效
- 必須改用**角色隔離 + 事先寫死的清單式審查契約 + 不同 prompt 焦點**來防止橡皮章
- 先用一個最廉價的試探性 spawn 驗證模型覆寫是否可用，再正式派工，**避免整批派工失敗**

### 9.3 Fork 與並行槽位

- **shard 數 ≤ 維度分組數**，且每個 shard 必須對應到 spec 的維度，不得重疊。
- `fork_context=false` + 讓 sub agent **自行讀檔**（spec、log）通常優於把全文塞進 prompt：省 token、且保證它們看到的是同一份凍結版本。
- sub agent **必須**收到完整作業規範（標籤規則、禁止事項、輸出格式、輸出路徑），不能假設它們看過對話。
- Reviewer 建議**常駐不關閉**，以維持跨 pipe 的一致裁定脈絡；但若並行槽位吃緊，可在 gate 前關閉、gate 時重 fork 並附上前一輪審查摘要作為 context。
- `wait_agent` 一次可傳多個 target，用最長 timeout 等第一個完成者，不要用短 timeout 輪流試探。

## 10. 已知失效模式與防護

以下皆為實測踩過的坑，直接沿用防護可省下整輪返工。

| # | 失效模式 | 徵狀 | 防護 |
|---|---|---|---|
| 1 | **sub agent 代需求者決定** | Reviewer 直接給出需求答案並往下走 | spec 明寫「不得代決」；Planner 轉交時保留選項按鈕，由需求者按 |
| 2 | **無共同基準，各 shard 各自漂移** | 同一份報告建立在不同版本的「大勝」定義上 | spec 寫入**量化操作性定義**，讓層 A 與層 B 共用同一基準 |
| 3 | **前提與事實混寫** | 情境推演被讀成已發生的事實 | 強制雙層結構，審查列為首要查核項 |
| 4 | **文件端腦補** | 研究缺口被模型自己的知識填滿 | spec 明禁；文件端寫「查無資料」並附附錄；Reviewer 逐條比對研究筆記編號 |
| 5 | **維度表混類** | 同一格既是影響又是證據來源，shard 寫法不一致 | 維度重構為「影響維度／反饋反制／影響時程／參照案例」四類欄位 |
| 6 | **缺時程維度** | 「影響」變成無時點的模糊陳述 | 每項影響必標：數日內／數月內／一至四年 |
| 7 | **缺混淆因素切割** | 同期非選舉事件被歸因給選舉 | 每項影響標歸因強度（選舉直接／間接／背景因素）＋ 專節收納非選舉因素 |
| 8 | **審查變成橡皮章** | Reviewer 說「大致 OK」就放行 | 結構化 verdict ＋ 精確定位 ＋ 清單式審查項目 |
| 9 | **無限迴圈** | 研究審反覆退回改到天荒地老 | 每 pipe 上限 3 輪，第 3 輪升級需求者決策 |
| 10 | **時序基準矛盾** | 投票日與執行日寫法不一致，引用合法性存疑 | spec 固定「引用截止時點」，所有數字標明截止時間 |
| 11 | **只寫預測宣稱** | 「兩院過半」被寫成既成事實，但正式認證可能為 0 席 | 報告須**並呈**預測宣稱與正式認證進度兩個欄位 |
| 12 | **模型覆寫失敗導致整批派工失敗** | 所有 spawn 立刻報 unknown model | 先用最廉價試探 spawn 驗證，再正式派工 |
| 13 | **shard 交接時素材無法回溯** | 文件端引用研究筆記但對不上編號 | 強制 `S<n>-#<N>` 連續穩定編號，文件端須標編號 |
| 14 | **紀錄留白** | log 只有表格沒有細節，事後無法稽核 | 每 pipe 追加：輸入、輸出、verdict、重試次數、回退決策、agent ID |
| 15 | **需求者中途追加交付物** | 新增產出不在凍結 spec 的交付清單內 | 不改 spec，另立附帶產出並在 log 標註為「需求者追加，非 spec 變更」 |

## 11. 快速啟動 Checklist

### 開始前

- [ ] 建立專案目錄與 `PIPELINE_LOG.md`
- [ ] 確認 `spawn_agent` 的模型覆寫是否可用（試探一次）
- [ ] 確認可並行槽位數（影響 shard 切分）

### Pipe 1（需求與規格）

- [ ] Gate 1 需求意圖確認（options block）
- [ ] fork Reviewer 做問答式需求審查
- [ ] 轉交需求者拍板（決策 pack，含建議預設答案）
- [ ] 寫 spec（§8 清單全覆蓋）
- [ ] Gate 2 核准 → spec 凍結（FROZEN）

### Pipe 2（研究）

- [ ] shard 切分對應維度，寫入 log
- [ ] 每個 shard prompt 內含完整取證規範與輸出路徑
- [ ] 收齊後 fork Reviewer 審研究，審查項目對照 spec 審查基準
- [ ] 不通過 → 回 2.2，計入迭代輪次

### Pipe 3（文件）

- [ ] 派工時附 spec + 已核准研究筆記
- [ ] 產出後 fork Reviewer 審查（正確性／完整性／雙層分離／可回溯／結構／美化／多格式一致）
- [ ] 不通過 → 回 3.2

### Pipe 4（交付）

- [ ] #1 + #2 最終確認
- [ ] 決定是否回退
- [ ] 通知需求者：交付連結 + 審查摘要
- [ ] 補齊 `PIPELINE_LOG.md`，確認每個 pipe 皆有紀錄

## 12. 最小可行變體

時間或槽位有限時，可縮減為：

```
1.1 Gate 1 → 1.2 Reviewer 需求審 → 1.3 spec → Gate 2
2.1-2.2 單一 Researcher（不拆 shard，但維度要全覆蓋）
2.3 Reviewer 研究審
3.1-3.2 Document maker → 3.3 Reviewer 文件審
4.1-4.3 交付與紀錄
```

**不可縮減的部分**：Gate 1、Gate 2、兩道 Reviewer 審查、審查契約、append-only 紀錄。縮減的是 shard 數與規格篇幅，不是關卡本身。
